# Telegram without judge bot access: system and walkthrough

## Two separate modes

| Area | Judge-facing browser practice | Real private Telegram companion |
| --- | --- | --- |
| Entry | `/telegram/demo`, linked from Telegram companion | Operator-configured allowlisted private account |
| Account/token | None required | Privately configured bot token and numeric owner ID |
| Data | Fresh disposable Atlas fixture per browser workspace | Explicitly paired existing local/visitor workspace |
| Commands | Supported command parser and example buttons | Existing deterministic commands; optional qualified model translation |
| Financial results | Actual deterministic tools and validators | Same deterministic engine/tools |
| Delivery | Simulated cards in the browser; no Telegram request | Real Telegram transport, update identity and durable outbox |
| Approval | Human practice button; exact snapshot only | Existing private owner button; exact snapshot only |
| Persistence | Memory-only lesson; 30-minute lifetime | Existing financial/control SQLite and normal expiry rules |
| Alerts | Explicit on-demand recalculation button | Opted-in worker notifications while service runs |

The browser demonstration is not evidence of a new live Telegram delivery or live-model response. Every screen labels **SIMULATED TRANSPORT · NO LIVE AI**. Financial results are computed, not prerecorded model prose. The shared Telegram card formatter is reused, with escaped rendering restricted to bold/code text. Replies that refer to a linked browser should be read within this disposable practice context; the Practice results/evidence panel is authoritative for this lesson.

## System flow

1. Hosted admission supplies the existing isolated browser workspace/cookie and CSRF. The practice object is stored only on that server-selected workspace, with a fresh separate synthetic ledger. No public form selects a database path, business, role or real bot.
2. Supported `/forecast`, `/plans`, `/draft`, `/snapshot`, `/status`, `/alerts on|off` commands are parsed locally. Unknown text is explicitly not interpreted by AI. Commands cannot approve payments or grant consent.
3. DRAFT/snapshot proposals run the existing guided-plan validation on a private copy. The exact terms, financial revision, 15-minute expiry and opaque review token are stored in practice memory. The initial card creates no DRAFT or saved snapshot.
4. A human review button invokes existing validated tools on a copy of the practice ledger, committed to the practice object only on success. DRAFT remains DRAFT. A snapshot request first creates a pending workflow, then needs a second exact owner approval through the existing `workflows.decide` function. Only `save_forecast` is eligible. Actors/audit labels say `telegram-demo-*`, never real Telegram delivery.
5. Changed data, expired/unknown/repeated reviews and cross-lesson tokens cannot execute a fresh operation. Request IDs bind exact form content, so repeated submissions are no-ops and altered replay is refused. Restarting the lesson invalidates old forms/buttons. Existing Host/Origin/CSRF protection remains.
6. On-demand alerts require opt-in. Forecast payloads are recomputed with the existing tool and hashed to avoid duplicate forecast notifications. The explicit synthetic delay button changes only practice timing. No scheduler, external notification, invented receipt or money movement is added.

The module does not import a network client or open a database. It never reads `server.telegram`, connection settings, environment credentials or the active model. It calls no external provider. Each lesson has at most 100 operation identities, 40 displayed messages and 20 pending reviews; the visitor cache/capacity remains bounded. Reset/expiry/server restart may discard practice results, which are deliberately not main-ledger business records. The real private integration keeps its existing persistence and authority checks.

## Suggested judge walkthrough (about 2–3 minutes)

1. Open Telegram companion → **Open Telegram interactive demo**. Point to the simulation/no-live-AI label and separate practice-data explanation.
2. Press **View forecast**. Inspect currency-qualified balances/dates and evidence IDs; compare plans if time permits.
3. Press **Prepare sample DRAFT**. Show exact invoice, currency, amount and date. Note the DRAFT count is still zero. Press **Create practice DRAFT**; inspect its DRAFT-only state in Practice results.
4. Press **Request snapshot**. Press **Prepare pending snapshot**; show that no snapshot is saved yet. Inspect the second card's forecast/steps and press **Approve & save practice snapshot**. A separate human choice saves one synthetic snapshot and leaves recorded cash unchanged.
5. Press **Enable practice alerts**, then **Check practice alerts**. Apply the explicit synthetic customer delay and check again. The forecast changes in practice; repeated checks do not create duplicate forecast notifications.
6. Optionally prepare a review, apply the delay, and try the old button to demonstrate stale-data refusal. Restart the disposable lesson without touching main records or the real bot.

Never describe this as a real Telegram message, unrestricted autonomous AI action, real payment or source authentication. If showing the private bot separately, label its live evidence separately; judges do not gain private access from this practice page.
